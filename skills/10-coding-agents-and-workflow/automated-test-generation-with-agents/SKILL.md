## Usage
### Architectural Purpose
Unit testing legacy codebases is highly tedious. AI coding agents equipped with execution tools (like Aider, Claude Code, or Antigravity) can autonomously generate test cases, run the test suite, analyze the compilation/assertion errors, and iteratively fix the code until 100% coverage is achieved.

---

### 1. Core Pattern / Implementation

### The Agentic TDD Loop
1. **Analyze**: The agent reads `MyService.java`.
2. **Generate**: The agent writes `MyServiceTest.java` using JUnit 5 and Mockito.
3. **Execute**: The agent runs the shell command: `mvn test -Dtest=MyServiceTest`.
4. **Evaluate**: The agent captures `stderr` and `stdout`.
   - If tests pass -> End loop.
   - If tests fail -> The agent modifies the test or the source code and loops back to step 3.

### Prompt Convention for Agents
Provide the agent with a strict constraint file (`.agent-rules.md`) at the root of the project:

```markdown
- Always use JUnit 5 and AssertJ.
- Use `@ExtendWith(MockitoExtension.class)` for mocks.
- Never use `@SpringBootTest` for unit tests; use standard constructor injection.
- Run `mvn test` after writing the file. Do not ask for permission.
```

---

### 2. Cost, Latency & Trade-offs
- **Token Math**: The iterative loop consumes significant tokens. A 4-step failure-fix loop can easily consume 20k input tokens as the agent repeatedly reads the stack trace and source files.
- **Latency Penalty**: Compilation and test execution delays the agent's reasoning loop. A slow Maven build (e.g., 30 seconds) degrades the agentic workflow speed.
- **Trade-off**: The agent might write "tautological tests" (tests that mock everything so aggressively they just test the mock framework). Code reviews are mandatory to ensure semantic test quality.

---

### 3. Verification Checklist
- [ ] The agent runs tests in isolation to prevent polluting state.
- [ ] The workspace ignores compilation output (`target/`, `bin/`) so the agent does not accidentally read generated bytecode.
- [ ] Infinite loop circuit breakers are configured (e.g., max 5 test-fix iterations) to prevent runaway billing.
